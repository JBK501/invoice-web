# Claude 명령어: Test

특정 언어/프레임워크에 종속되지 않고, 프로젝트에서 이미 사용 중인 테스트 도구와 컨벤션을 감지하여 그에 맞는 테스트 코드를 작성하는 도구입니다.

## 사용법

```
/test                     # 최근 변경된 코드에 대한 테스트 작성
/test [파일 경로]           # 특정 파일에 대한 테스트 작성
/test --coverage          # 기존 테스트의 커버리지 갭 분석 및 보완
```

## 프로세스

### 1. 프로젝트 테스트 환경 감지

- 설정 파일, 의존성 목록, 기존 테스트 파일의 확장자/구조를 확인하여 사용 중인 테스트 프레임워크와 스타일 파악
- 기존 테스트 파일이 있다면 네이밍 규칙, 폴더 구조, assertion 스타일을 그대로 따름
- 감지되지 않으면 대상 코드의 언어에서 가장 널리 쓰이는 프레임워크를 사용하고, 사용한 프레임워크를 명시

### 2. 대상 코드 분석

- 함수/메서드의 입력, 출력, 부수효과(side effect) 파악
- 분기문, 반복문 등 로직 흐름 파악하여 테스트해야 할 경로 식별
- 외부 의존성(네트워크, DB, 파일 시스템, 시간 등) 파악하여 목(mock)/스텁 필요 여부 판단

### 3. 테스트 케이스 설계

아래 기준으로 빠짐없이 케이스를 도출:

- **정상 케이스**: 일반적인 입력에 대한 기대 동작
- **경계값 케이스**: 빈 값, 0, 음수, 최대/최소값, null/undefined
- **예외 케이스**: 잘못된 입력, 예외 발생 상황, 에러 핸들링
- **비동기/동시성 케이스**: 해당되는 경우 타이밍, race condition
- **회귀 케이스**: 버그 수정 코드라면 재발 방지용 케이스

### 4. 테스트 코드 작성

- 프로젝트에서 감지된 프레임워크 문법으로 작성
- 각 테스트는 하나의 관심사만 검증 (단일 책임)
- 테스트명은 "무엇을 검증하는지"가 명확하게 드러나도록 작성
- 필요한 mock/stub/fixture 포함

### 5. 결과 요약 제공

## 출력 형식

```
## 🔍 감지된 테스트 환경
- 프레임워크: [예: Jest, pytest, JUnit 등]
- 기존 컨벤션: [파일 위치, 네이밍 규칙 등]

## 🧪 작성된 테스트 케이스
| 구분 | 설명 |
|------|------|
| 정상 | ... |
| 경계값 | ... |
| 예외 | ... |

## 📄 테스트 코드
[생성된 테스트 파일 전체 코드 또는 diff]

## ⚠️ 커버되지 않은 부분 / 한계
- [수동 확인이 필요하거나 목(mock)으로 대체한 부분 명시]
```

## 규칙

- 실행 환경을 추측해서 임의로 새 프레임워크를 도입하지 않음 (이미 있는 도구 우선)
- 테스트가 구현 세부사항이 아닌 동작(behavior)을 검증하도록 작성
- 과도한 mock으로 실제 로직 검증을 회피하지 않음
- 하나의 테스트 실패가 다른 테스트에 영향을 주지 않도록 독립적으로 작성
- 테스트 코드에도 가독성 있는 네이밍과 최소한의 주석 적용
